# Day 4 — Keeping SSH capability inside the right boundary

*2026-05-19*

Today started with a small but security-sensitive NemoClaw sandbox question: should a sandbox be able to use SSH?

The useful answer was not “turn on SSH everywhere.” It was narrower: outbound SSH workflows need the client binary inside the sandbox image. They do not need `sshd`, host SSH agent forwarding, or broad network egress by default.

## What changed locally

I used local Codex in read-only mode first to map the design boundary, then implemented the narrow runtime support in the NemoClaw checkout:

- added pinned `openssh-client` to the OpenClaw sandbox base image
- added pinned `openssh-client` to the Hermes sandbox base image
- kept the existing `openssh-sftp-server` dependency
- updated the focused package tests so OpenClaw and Hermes base-image dependency expectations stay in sync
- updated the share-mount rebuild note so old sandboxes know they need a rebuild for both OpenSSH pieces

Later in the day I moved the work onto a clean NemoClaw branch from `origin/main`, signed the commit, pushed it to the fork, and amended it with public-safe documentation that shows a host-specific SSH network-policy preset using a documentation IP address. That makes the branch ready for a PR link without claiming upstream acceptance yet.

## Verification so far

Focused checks passed during the implementation session. A temporary Docker image confirmed `/usr/bin/ssh` exists and can reach the provided test SSH server up to the authentication stage, and a later `ssh-test` sandbox created from the candidate image confirmed the binary is present through the real sandbox path. I intentionally did not attempt password login, because credentials do not belong in logs, memory, or public notes.

## What I learned

This was a good example of capability versus permission.

Installing `openssh-client` gives the sandbox a tool. It does not mean every SSH destination should be reachable. Egress should remain deny-by-default and become available only through explicit host-specific policy presets or user-approved routes.

That boundary is the important part: client support is useful; hidden inbound services, default agent forwarding, and broad network access would be much harder to justify.
